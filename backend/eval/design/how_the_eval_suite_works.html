How the eval suite works

The evaluation has three parts: text-based, vision-based, and audio-based. Text-based questions are built by crossing two axes, capability and phrasing, then delivered either as a single message or split across multiple turns, so text-based splits into a Single-turn and a Multi-turn section below. Vision uses a separate model on photo input. Audio tests a transcription layer feeding into the same chat agent.

Single-turn

Every single-turn question is placed by crossing two axes — capability (what the agent has to do) and phrasing (how the message arrives) — then weighted toward where testing found real fragility, not spread evenly. 50 total, fixed target.

Axis A — Capability

What the agent has to do. 7 rows. Multi-turn is not one of them — it's a harness difference, not a capability.

Factual lookup

Directly answerable from one knowledge-base entry.

Synthesis

Needs several knowledge-base entries pulled together, without dropping or inventing any.

Amap API

Needs a live routing call for a real answer.

Chit-chat

Off-topic small talk, staying in role.

Knowledge base boundary

Admits "I don't know" instead of inventing a believable answer.

Adversarial

Resists an attempt to override the system prompt or break role.

Recommendation

An open-ended generative ask — naming a real shop, not confirming/denying one that was named.

Axis B — Phrasing

How a single message arrives, independent of what it's testing.

Short

One clean clause, minimal setup.

Long

One intent wrapped in real context, several constraints at once — still one ask.

Multi-intent

Two or more distinct asks bundled in one message. Standard bundle size is 2; one case in the 50 uses 3, written plainly rather than flagged as an exception.

Ambiguous

Inconsistent phrasing (self-contradictory, self-correcting, wandering) is the only flavor used — disfluent filler (那个/呃/嗯) is a speech-transcription artifact, not how someone types, so it never appears in a typed question.

Multi-turn

"Needs multiple turns" splits into 3 categories, because it was never one thing.

needs-history-to-parse

A pronoun or referent with no antecedent outside the conversation — the question is grammatically incomplete without a prior turn to resolve it. Sourcing this from the main grid is one option: take a 50-question verbatim, swap its one named entity for a pronoun, prepend a turn 1 that names the entity. Worked example — factual_multiintent_01: "Pie Bird西岸梦中心店除了派还卖咖啡吗？" becomes "那家店除了派还卖咖啡吗？" with a prior turn naming the branch. A freshly-written question works just as well, as long as it's genuinely unparseable without the prior turn.

distance-erosion

The exact same main-grid question, verbatim, delivered as the final message after a shared filler conversation (real, unrelated dessert-shop chat) — testing whether the answer still holds at conversational distance, not whether it can be parsed. This one is never freshly written: reusing the main grid word for word is the definition of the tag, since the whole mechanism is a direct comparison against that question's own single-turn answer. Two probes (a plain baseline, a harder variant of the same capability) × two distances (5-turn, 10-turn) × 6 categories.

personalization-recall

A preference stated once, never repeated, tested for whether it survives in conversational memory without being restated — a distinct mechanism from a seeded-database-history test. Sourcing this from the main grid is also just an option, not a requirement: split an existing question's constraint from its ask and deliver them turns apart, or write fresh content entirely — either is valid as long as the preference genuinely has to survive at a distance.

What each distance-erosion contrast isolates, by category: KB boundary — does a longer, context-wrapped "admit you don't know" erode faster than a bare one. Adversarial — refusal alone vs. refusal while still answering a bundled real question correctly, a harder discrimination task under the same distance. Recommendation (no-signal) — does messier phrasing compound with distance to raise the fabrication rate beyond what plain no-signal already risks. Factual lookup — does a single fact survive filler more reliably than the second fact in a bundled answer. Synthesis — does juggling several constraints at once make aggregation more likely to drop or invent an entry after filler. Amap — does the tool call stay reliable either way, and does a bundled follow-up survive alongside the route as reliably as the route alone.

The needs-history-to-parse cases, the full distance-erosion table (shared filler + every probe), and the personalization-recall cases (matcha preference, mobility constraint, chocolate allergy) are in backend/eval/design/eval_question_bank_draft.md.

Vision-based evaluation

A different model entirely (qwen-vl-max, photo in) — not crossed with either text axis above, and not split into single/multi-turn the way text is. Sub-shapes are concentrated where testing found an actual open bug or an untouched attack surface, not spread evenly.

Every case needs a real, hand-sourced photo — pulling one off the web and presenting it as a real test asset would undermine the point of the eval.

Audio-based evaluation

A live-mic voice input feeding into the same chat agent (DashScope ASR), with the transcript shown to the user for editing before it's sent — that review step is itself part of the design, since it changes what the highest-value test cases look like.

The review-before-send detail matters: it catches an obviously garbled or empty transcript before the agent ever sees it, the same way nobody sends a text message with a typo they noticed. So the highest-value cases aren't "any" transcription error — they're a mistranscription that still reads as a coherent, plausible question, the kind a quick read-back wouldn't catch. Same "confident-wrong beats obvious-garbage" pattern the rest of this design already chases, in text and in vision.

ASR transcript accuracy — no agent involved

Transcript-in, expected-text-out, tested against how real speech actually varies:

  • Filler words (呃/嗯/那个)
  • Self-contradicting or inconsistent statements
  • English-Chinese mingling within one statement
  • Soft, quiet speech
  • Fast speaking speed

Agent behavior on a plausible-wrong transcript — reaches the agent

Seed the exact transcript a mishearing would produce, not the audio itself, and check the agent's reply. Flagship case: a code-switched brand name misheard as a different real KB brand — does the agent answer confidently about the wrong shop.

Two things stay out of scope here, on purpose, because the review step moves them to a different layer. Silence/heavily-garbled audio is a frontend question (does the recording UI clearly show "nothing was heard"), not something the agent needs to handle. Voice-delivered prompt injection reduces to ordinary text once transcribed — the existing Adversarial category already covers it, and the review step only sharpens that, since the visitor sees the injected text as plain chat content before ever sending it.

Design principles

Follow these when adding, weighting, or phrasing any eval question — text, vision, or audio.

Crossing isn't mandatory

Don't fill a phrasing tag, delivery form, or bundle-size cell just to make the matrix look complete. Add a case only if it reads like something a real person would actually say; leave a gap alone otherwise.

Weight goes where testing found fragility

Knowledge base boundary and Recommendation carry more weight than the rest because repeat sampling found real, documented failure rates there. Synthesis, Amap, and Chit-chat stay lean because nothing in testing suggests they need more — extra samples on an already-stable case mostly buy false confidence, not signal. Weight new cases the same way: point them at a documented failure, not at whichever category looks thin.

Main-grid reuse is an approach, not a mandate — except for distance-erosion

For needs-history-to-parse and personalization-recall, building from a 50-question is the easiest way to get a checkable ground truth for free — but a freshly-written question is equally valid as long as it genuinely tests the mechanism and comes with its own ground truth. Distance-erosion is the one exception: the entire mechanism is a comparison against an exact single-turn sibling's answer, so reuse there isn't a convenience, it's the definition of the tag.

Sound-check before committing

Read every new question back like a real user would say it out loud. Backend language ("你们收录了……这个牌子吗？" — "is this brand indexed?") reads as system language a real visitor wouldn't say — that's a drafting bug, not a legitimate test variant, so rewrite it into something an actual customer would ask rather than keeping it as-is.

Eval-awareness is a separate track, not a phrasing variant

Whether the agent answers differently when a question signals it's being tested vs. a genuine customer voice is a real, distinct thing worth measuring — a small paired set, same fact asked naturally vs. with an explicit tell. Keep it as its own tagged track outside the main 50; don't smuggle backend jargon into an ordinary capability cell to test it.
