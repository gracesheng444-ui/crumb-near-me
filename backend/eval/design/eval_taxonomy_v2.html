Eval Taxonomy v2

The evaluation has 3 parts: text-based, vision-based, and audio-based. Text-based is the developed part — every question is built by crossing two axes, capability and phrasing, then delivered either as a single message or split across multiple turns, so text-based splits into a Single-turn and a Multi-turn section below. Vision and audio are sketched as placeholders for now; their detail gets filled in later.

Single-turn

Every single-turn question is placed by crossing two axes — capability (what the agent has to do) and phrasing (how the message arrives) — then weighted toward where testing found real fragility, not spread evenly. 50 total, fixed.

Axis A — Capability

What the agent has to do. 7 rows. Multi-turn is not one of them — it was never a capability, just a harness difference that used to live in the wrong axis.

Factual lookup

Directly answerable from one knowledge-base entry.

Synthesis

Needs several knowledge-base entries pulled together, without dropping or inventing any.

Amap API

Needs a live routing call for a real answer.

Chit-chat

Off-topic small talk, staying in role.

Knowledge base boundary

Admits "I don't know" instead of inventing a believable answer.

Adversarial

Resists an attempt to override the system prompt or break role.

Recommendation

An open-ended generative ask — naming a real shop, not confirming/denying one that was named.

Axis B — Phrasing

How a single message arrives, independent of what it's testing.

Short

One clean clause, minimal setup.

Long

One intent wrapped in real context, several constraints at once — still one ask.

Multi-intent

Two or more distinct asks bundled in one message. Standard bundle size is 2; bundle size is otherwise just a number, not a special category — one case in the 50 uses 3, written plainly rather than flagged as an exception.

Ambiguous

Inconsistent phrasing (self-contradictory, self-correcting, wandering) is the only flavor used now, everywhere. Disfluent phrasing (那个/呃/嗯 filler words) is a speech-transcription artifact, not how someone types — it doesn't belong in this category at all, and every question that used to carry it has been rewritten.

Multi-turn

The 50 table stays 100% single-turn — every question there is exactly what it says, nothing swapped out for a conversation. On top of it, three tags test three different ways multi-turn context can go wrong. 34 cases total (7 + 24 + 3):

needs-history-to-parse 7

A pronoun or referent ("那家店", "他们家") with no antecedent outside the conversation — the question is grammatically incomplete without a prior turn to resolve it. Tests reference resolution.

distance-erosion 24

A self-contained question, meaning the same thing regardless of position, delivered after N turns of unrelated filler instead of first. Tests whether a correct answer decays with distance.

personalization-recall 3

A self-contained, generic-looking ask whose correct answer depends on a preference or constraint stated several turns earlier and never restated. Tests whether that earlier context silently keeps shaping behavior.

needs-history-to-parse 7 cases

Definition: a pronoun or referent ("that one", "他们家") with no antecedent outside the conversation — the question is grammatically incomplete without a prior turn to resolve it.

How to build one: reusing the main grid is a convenient approach, not a requirement. Take a 50-question's text unchanged, find the one named entity in it, and replace only that entity with a pronoun (他们家 / 那家店 / 这家店 / 这个牌子 / 这两个牌子 — whichever reads naturally in that grammatical slot), then prepend a new turn 1 whose only job is to name that entity. Worked example, factual_multiintent_01: original — "Pie Bird西岸梦中心店除了派还卖咖啡吗？开到几点？" Swap "Pie Bird西岸梦中心店" for "那家店" and touch nothing else — "那家店除了派还卖咖啡吗？开到几点？" Doing it this way gets a checkable ground truth for free — the expected answer is just the main-grid question's own answer — which is why all 7 cases below happen to be built this way. But it's not the only valid way to write one: any question that's genuinely unparseable without a prior turn qualifies, main-grid-derived or not; a freshly-written one just needs its own expects spelled out instead of inheriting a sibling's.

distance-erosion 24 cases

Definition: the question is self-contained and means the same thing regardless of position — what's tested is whether the correct answer still holds once the question isn't the first thing asked.

How to build one — this one is a rule, not an option: every probe must be the exact wording of an existing single-turn (main-grid) question, wrapped in filler and delivered later in the conversation. That's what makes the comparison meaningful — the multi-turn reply is graded against that exact same question's own single-turn answer, so any difference is attributable to distance alone, not to a different question being asked. There's no freely-written version of this tag the way there is for the other two. Started at 3 categories (the ones with a documented failure pattern); extended to 3 more (Factual, Synthesis, Amap) since erosion is worth checking even where nothing's failed yet — a stable case that erodes under filler is exactly the kind of thing a single clean run would never catch. (Renamed from "refusal-erosion" — that name only fit the original 3 categories, where the correct behavior actually is a refusal; for Factual/Synthesis/Amap the correct behavior is a positive, correct answer, so "refusal" stopped describing what's being tested. "Distance" is the part that was always accurate.)

The 12 probes, and why each A/B pair is built the way it is

Probe A and Probe B are never two arbitrary picks from the same category — in every one of the 6 categories, A is the plain, single-ask version of that capability and B is a harder variant of the exact same capability (bundled into a multi-intent, wrapped in long context, or phrased with a self-correction). Holding the capability and both filler lengths constant while varying only "how complex was the question" isolates a second question distance-erosion alone can't answer: does added complexity make erosion worse, or does distance-from-start affect a clean question and a messy one equally?

personalization-recall 3 cases — additive, not a slot

Definition: the question is fully self-contained — nothing to parse, so it isn't a needs-history case either. It tests whether a preference survives in conversational memory, without being re-stated, a distinct mechanism from recommendation_short_02's seeded-DB-history test.

How to build one: like needs-history-to-parse, reusing the main grid is a convenient approach, not a requirement — take an existing 50-question, split its constraint from its ask, and deliver them turns apart instead of together. The mobility case below is the clean version of this: amap_long_01's "腿脚不太方便，不想走太远的路" constraint and its "从徐家汇地铁站到武夷路的EAU Café怎么走" route request, split onto turn 1 and turn 5 with 3 turns of real conversation in between. The matcha and allergy cases mix that same idea with freshly-written content instead (no 50-question states a chocolate allergy) — both are equally valid, since the point is whether the preference survives, not where it came from. No guaranteed single-turn sibling to diff against here, so these are graded directly against their own expects rather than as a delta.

Audio-based evaluation planned, 0 cases yet

No longer purely hypothetical — a live-mic voice input is planned for the chat page (DashScope ASR, Qwen3-ASR-Flash/Fun-ASR, matching the guess this section already had), with the transcript shown to the user for editing before it's sent. Still nothing to run yet: no audio-upload or transcription call exists in the codebase today, and the only current audio integration is speak (text→voice output, via ElevenLabs). This section stays a design sketch until the pipeline exists, not a task to start now — but the review-before-send detail already changes what these cases should look like once it does.

That review step matters: it catches an obviously garbled or empty transcript before the agent ever sees it, the same way nobody sends a text message with a typo they noticed. So the highest-value cases aren't "any" transcription error — they're a mistranscription that still reads as a coherent, plausible question, the kind a quick read-back wouldn't catch. Same "confident-wrong beats obvious-garbage" pattern the rest of this design already chases, in text (hallucination under plausibility) and in vision (a confident wrong brand guess). The natural shape mirrors Vision's own split between a narrow model-accuracy check and a downstream agent-behavior check:

ASR transcript accuracy no agent involved

Transcript-in, expected-text-out — same shape as identify_exhibit's own accuracy check, separate from any chat follow-through. Sharpest case: a Latin-script brand name spoken inside a Chinese sentence (Pie Bird, EAU Café, bebaked) — code-switching is a distinct, app-specific error mode from a plain Chinese homophone slip. Also worth checking here, not downstream: whether the ASR normalizes away spoken disfluency (那个/呃/嗯) or transcribes it verbatim, and whether a number (an address, a price, an hour) survives intact.

Agent behavior on a plausible-wrong transcript reaches the agent

Seed the exact transcript a mishearing would produce — not the audio itself — and check the agent's reply, the same way Vision's expects_chat follows through on expects_identify. Flagship case: a code-switched brand name misheard as a different real KB brand rather than gibberish — does the agent answer confidently about the wrong shop instead of the one actually meant.

Two things dropped out of the earlier sketch of this section now that a review-before-send step is part of the plan — not because they stopped being real failure modes, but because they moved to a different layer. Silence/heavily-garbled audio is now a frontend question (does the recording UI clearly show "nothing was heard") rather than something the agent needs to handle gracefully. Raw spoken disfluency reaching the agent verbatim would require the user to notice it in the transcript and send it anyway — worth an occasional check, but no longer the headline case now that ASR normalization is checked directly in the accuracy layer above. Voice-delivered prompt injection stays excluded for the same reason as before: once transcribed, it's ordinary text the existing Adversarial category already covers — the review step only sharpens that, since the user would see the injected text as plain chat content before ever sending it.

Design principles

What actually governs every decision above, condensed.

Crossing isn't mandatory

A phrasing tag, a delivery form, a bundle size — none of these are cells that must be filled. Every addition this round exists because it reads like something a real person would actually say, and every gap is left alone rather than padded to look complete.

Weight goes where testing found fragility

Knowledge base boundary and Recommendation grew because repeat sampling found real, documented failure rates there. Synthesis, Amap, and Chit-chat didn't grow because nothing in this session's testing suggested they needed to — more samples on an already-stable case mostly buys false confidence, not signal.

Main-grid reuse is an approach, not a mandate — except for distance-erosion

For needs-history-to-parse and personalization-recall, building from a 50-question (swap an entity for a pronoun; split a constraint from its ask across turns) is the easiest way to get a checkable ground truth for free, and it's how every existing case in both tags happens to be built — but a freshly-written question is equally valid as long as it genuinely tests the mechanism (unparseable without history; a preference that survives without being restated) and comes with its own expects. Distance-erosion is the one exception: it has no freely-written form, because the entire mechanism is a comparison against an exact single-turn sibling's answer — reuse there isn't a convenience, it's the definition of the tag. When writing a new multi-turn question, decide the tag first (see the three definitions above), then only reach for main-grid reuse where it's actually optional.

Sound-check before committing

Read every new question back like a real user would say it out loud before it's final. Caught twice this round: "你们收录了'哈根达斯'这个牌子吗？" and then, in the same session, the same "收录"/"知识库" backend language re-appearing in 3 of the newly-drafted KB-boundary questions (MUJI, Lady M, 宜芝多) — a pattern, not a one-off typo. All 4 are now rewritten as something an actual customer would ask (e.g. "上海哪里能买到哈根达斯呀，你知道吗？"), both here and in test_questions.json.

That's worth measuring on purpose someday — a small paired set, same fact asked naturally vs. with an explicit tell — but as its own tagged track outside the 50, not as incidental jargon inside ordinary capability cells.
